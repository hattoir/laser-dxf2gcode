## 1. 概要と数字

**何をするものか**: Fusion 360 の DXF(のちに STL にも対応)から、ダイオードレーザー
Creality Falcon2 22W(GRBL 1.1f)用の G-code を作る CLI。カーフ補正、内側→外側の切断順序、
加工エリア検査、生成後の安全検証、SVG プレビューを自動で行う。

**なぜ作ったか**: LightBurn の代替ではなく、「Fusion 360 で設計した板材部品を、寸法どおりに、安全に切る」
という用途に絞ったもの。ポートフォリオに載せる技術的な読み物も兼ねる。

**使う人**: 開発者本人(ロボット製作者。Serpens、auto-trash-navigator を設計している)。レーザー加工は初めて。

## 2. 2026-09-11 初期開発(タスク 0〜8)

「自律開発 / 制限時間 180 分」という指示書から始まった。安全に関する前提(エリア外なら G-code を
出さない、冒頭で安全な初期化、G0 で S0、SVG を目視してから流す、README に端材テストを明記)が
最初から設計原則として与えられていた。

### 環境の準備(タスク 0)

- **事実**: Windows 11 に Python が入っていなかった(`python` は Microsoft Store のスタブだけ)。
  `winget install Python.Python.3.12 --scope user` で 3.12.10 を導入(管理者権限不要、python.org 公式、ハッシュ検証済み)。
- `.venv` を作り、ezdxf 1.4.4 / pyclipper 1.4.0 / PyYAML 6.0.3 / pytest 9.1.1 を導入。
  SVG は依存を減らすため自前で書き出すことにした(svgwrite 不採用)。
- 人間に確認が必要な項目(出力 W 数、`$30`、エアアシストの M8/M9、材料)は `docs/TASK0_CHECKLIST.md` に
  まとめ、確認できるまでは設定ファイルに「仮定値」と明記して進めた。

### 実装(タスク 1〜8、コミット 02:21〜02:50)

| タスク | 内容 | 要点 |
|---|---|---|
| 1 | DXF 読み込み | 曲線を弦の許容誤差 0.05mm で直線近似、端点 0.01mm で連結、`$INSUNITS` が mm でなければ停止、OCS(押し出し方向 -Z)を正しく変換、重複輪郭を 1 本に |
| 2 | ツールパス | 入れ子の階層(偶数 = 外形、奇数 = 穴)、pyclipper でカーフ補正、深い階層から切る、同じ階層は貪欲法、リードイン |
| 3 | G-code | 生成前のエリア検査、生成後にテキストを別のパーサで読み直して安全検証(G0 の S0、発振中の G0、M3 禁止、末尾 M5 など) |
| 4 | プレビュー・レポート | プレビューは **生成済み G-code を読み直して** 描く(見た絵 = 流すコード)。所要時間は GRBL のプランナを簡略化して推定 |
| 5 | キャリブレーション | 20mm 角 ×4 のテストピース(設定値を刻印)、カーフ測定の細片、測定値をコメントを残したまま YAML に書き戻す |
| 6 | 設定ファイル | `machine.yaml` と `profiles/mdf_5mm.yaml`。すべての数値に【実測値】か【仮定値】を明記 |
| 7 | テスト | 安全に関わる 3 項目(切断順序・エリア検査・G-code の規則)を重点的に |
| 8 | README | 日本語。設計の要点を読み物として |

### この日の大きな判断: カーフ補正の向き

- **事実**: 指示書は「外形は内側へ、穴は外側へ k/2 オフセット(穴 R10 → R10.1)」。
- **判断**: これは向きが逆。レーザーの溝はパスの両側に k/2 ずつ広がるので、穴を外へずらすと
  仕上がりは R10.2 になり、補正なしより誤差が倍になる。指示書の目的(Ø4.2 の穴にボルトが入る)を優先し、
  **常に捨て側へ k/2** で実装した(穴 R10 → パス R9.9 → 仕上がり R10.0)。
- 最初に書いた README の説明は、途中で向きを取り違えた自己矛盾した文章だった。気づいて書き直した(→ 11 章)。
- **未確認**: 実物のテストピースが補正込みで 20.0mm 角になるかで確かめる(まだ測れていない)。

### この日の結果

- サンプル `samples/bracket.dxf`(部品 3、穴 9、入れ子 4 階層)で通し: 51 パス、推定 18 分。
- 原点が部品中心の `centered.dxf` は、エリア外として終了コード 2 で停止(G-code を出さない)。
- テスト 85 件。

## 3. 2026-09-27 刻印の分離と、実物の Fusion 360 DXF での試験

### 刻印を別ファイルで渡す(`--engrave`、`--as-layer`)

- **きっかけ**: Fusion のスケッチから書き出した DXF は全部がレイヤー「0」に入るので、刻印したい線を分けられない。
- 刻印用 DXF を重ねる `--engrave`、ファイル全体を 1 つの層にする `--as-layer` を追加。
  位置合わせは全ファイルまとめて行い、相対位置を崩さない(テストで確認)。
- 刻印フォントを A〜Z に拡張(それまで数字と一部の英字だけで、`PART 1` が書けなかった)。
- 「閉じていないパス」の警告を貫通切断の層だけに限定(刻印の線でも警告が出て、17 件が 1 件に減った)。
  本当に見るべき警告を埋もれさせないため。

### 実物の Fusion 360 DXF で試験

開いていた Serpens の設計から、穴径の実験用プレート「E Hole ladder」(60×30mm、Ø2.4〜Ø6.3 の穴 12 個)を
Fusion の API(`Sketch.saveAsDXF`)で書き出して試した。設計は変更していない。

| 分かったこと | 対応 |
|---|---|
| `$INSUNITS = 4`(mm)が入っている。座標も mm | そのまま読める |
| **スケッチ 1 つにつき DXF 1 ファイル**(板と穴が別ファイル) | `convert` を複数ファイル入力に対応 |
| 板が X=0 に接していて、カーフ補正で -0.079mm → **終了コード 2 で停止** | 設計どおりの挙動。`--align lower-left` で解決 |
| 12 穴の仕上がり径は設計値との差が最大 0.01mm | 直線近似の誤差の範囲 |
| 別スケッチの「コーナー切り欠き」が **穴として** 切られ、外形との間に 0.2mm の削り残し | 切断線どうしの近接を警告する `--min-gap` を追加 |
| 複数ファイルだと DXF のハンドルが重複して、警告の出どころが分からない | 輪郭の出どころにファイル名を付けた |

テスト 94 件。

## 4. 2026-09-30 実機の準備と、初めての切断

### 材料と板

- 材料の相談: 切ってよいもの・いけないもの(塩ビ、ABS、ポリカーボネート、スチレンボードなど)を整理。
- 板の大きさ: 加工エリアは 400×415mm。300×400mm 前後を勧めた。
- 100均の板: 練習用に使える、ただし「中質繊維板」表示・素の板・薄さ・品質のばらつきに注意、と回答。
- **事実**: ユーザーは 100均の MDF **2.5mm と 6mm** を購入。
- `profiles/mdf_2_5mm.yaml` と `mdf_6mm.yaml` を追加(値はすべて仮定値)。すべてのプロファイルに
  【実測値】/【仮定値】の注記があるかを検査するテストも追加。
- テストピースとカーフ細片が **同じ場所に重なる配置** になっていたのに気づき、細片の既定位置を Y=40 へ移した(テストで重ならないことを確認)。

### ミニごみ箱と、組み木の箱の生成(`box` コマンド)

- 「ごみ箱をいい感じに小さく」という依頼。手元の `auto-trash-navigator` に `dustbin.stl`(200×200×148mm、
  3D プリント用、上部 200 角・薄肉 + 下部 Ø138 の足)があった。
- レーザーでは丸い角・薄肉は作れないので、**同じ比率の 1/2(100×100×高さ 74mm)の組み木の箱** にした。
  足(ロボットの天板に差し込む部分)は、単体で置く小型版では省いた。
- 組み木の「どの板の指がどこを受け持つか」の規則を決め、**5 枚を 3D に組んで、辺と角のどの点も
  ちょうど 1 枚だけが占める** ことを検査するテストを書いた。
- **このテストがバグを見つけた**: 板厚 2.5mm が内部で 2mm に切り捨てられていた(→ 10 章)。

### 機械の設定を確認(LaserGRBL で `$$`)

| 項目 | 結果 |
|---|---|
| `$30` | 1000(仮定どおり) |
| `$32` | 1(レーザーモード有効。M4 が正しく効く) |
| `$11` | 0.010 |
| `$120/$121` | **1000/1000**(当初の情報の 500 は誤り。時間推定だけに影響) |
| `$154/$155` | 1/1(火焔・レンズ汚れの警報は有効) |
| `$153` | **0**(気流低下の警報は無効 → 有効化を推奨) |
| `$20` | **0**(ソフトリミット無効 → 有効化を推奨) |
| `$22/$23` | 1/3(ホーミング有効、原点は X・Y の最小側) |
| 出力 | 本体ラベルで **22W** |

### LaserGRBL と機械の操作

- コンソールの場所を案内するため画面を見たとき、**LaserGRBL を二重に起動してしまった**(→ 11 章)。
- AIR ランプの赤い点滅: 公式 Wiki で「待機 30 秒でポンプが止まると赤く点滅するのは正常」と確認。
- 置き場所の確認: レーザー OFF で使用範囲をなぞる `*_frame.gcode` を、テストピースとカーフ細片にも出すようにした。
  ヘッドを最初の角まで動かして止めるだけのファイル(`goto_start.gcode`)も作った。**枠確認は成功**。
- 焦点: 最初は一般的な「ヘッドの柱を板に当てる」方式で説明したが、**Falcon2 は段付きの金属ブロックを使い、
  切断は板厚と同じ目盛りの段で合わせる** のが正しかった(公式 Wiki・フォーラムで確認)。
  1〜2 回目の試験は誤った方法で焦点を合わせていた可能性が高い(→ 11 章)。

### 初めての切断(詳細は 8 章)

2.5mm の板でテストピースを切り始めたが、**FIRE(火焔検知)で止まる**、**下まで貫通しない**、が続いた。
3 回目の後、ユーザーから「**シールを剥がすのにアルコールを使った**」と聞き、有力な原因になった
(MDF はアルコールを吸い込み、アルコールの炎は明るい所ではほとんど見えない)。
6mm の板(アルコールなし)では、600mm/min・1 周で約 1mm 切れた(手触り)。

この間に足した対策:

- **`--pass-mode cycle` をキャリブレーションと箱にも**: 1 つの輪郭を続けて焼かず、全部を 1 周ずつ順に回る(熱がこもりにくい)
- テストピースの条件を「速め・多周回」に変更

## 5. 2026-09-30 切れない原因の検証と対策

依頼: 「原因と解決方法を考えて。無理なら切る部分を刻印して手でやる用の G-code と加工のやり方も。
なるべくレーザーでやりたいので、ソフト側・レーザーカッター側・100均の MDF など、いろんな要素を検証して」

### 検証したこと

- **ソフト側**: 止まったファイルを解析。止まったまま発振する箇所 0、M4 の直後に動かない箇所 0、
  送り速度の指定漏れ 0、S 値は想定どおり。**G-code に不備はなかった**。
  LaserGRBL の出力の上書きも 1.00 倍で問題なし。
- **メーカーの基準**: Creality 公式の Falcon2 22W 切断条件(シナ 2mm/700、3mm/550、5mm/400、8mm/240、
  10mm/120mm/min、すべて 100%・1 周)を入手。「1 周で切れる厚さ ≈ 1700 ÷ 速度」でほぼ説明できる。
  同じページに「切断時は材料の下を浮かせる(ハニカム台)」と明記。
- **材料**: 6mm MDF の実測(600mm/min・1 周で約 1mm)と比べると、**100均 MDF はシナの約 2.8 倍切りにくい**(暫定)。
  - MDF 2.5mm ≈ シナ 7mm 相当 → 十分切れる範囲
  - MDF 6mm ≈ シナ 17mm 相当 → 公式表の上限(10mm)を超え、**22W の限界付近**
- **結論(推測を含む)**: 当初の条件はエネルギーとしては足りていた。足りなかったのは焦点と熱のかけ方。
  FIRE の原因はアルコール・熱のこもり・板の下で燃えている、のどれか(重なりもありうる)。
  **本番は 2.5mm で作るのが現実的**。

### 足した機能

| 機能 | 目的 |
|---|---|
| `--cooldown 秒`(G4) | 発振のたびにレーザー OFF で待つ。検証器は「発振中の G4」「120 秒超」「P なし」を拒否。刻印の 1 画ごとには待たない(出力 50% 以上の後だけ) |
| `calibrate ladder` | 速度 × 周回の組み合わせを短い線で一度に焼き、光にかざして貫通する条件を探す。各マスのエネルギー指標とシナ換算の厚さを表示 |
| `--mark-only` / `score` 層 | 切らずに、切る線を浅く刻印するだけ(手で切るときの案内) |
| `box --joint butt` | 組み木なしの長方形 5 枚(手で切れる) |

生成したファイル: 6mm と 2.5mm の条件一覧試験、焦点の段を比べる線 4 本(`out/checks/focus_*.gcode`)、
手切り用のごみ箱(2.5mm はカッター用で隙間 0、6mm はのこぎり用で隙間 3mm)。

文書: `docs/TROUBLESHOOTING.md`(要素別の原因・対策・検証の順番)、`docs/MANUAL_CUT.md`(手で切る方法)。

作業中、シェルの引用符の解釈でパッチ用コマンドがまるごと失敗した(何も変更されなかった)。
以後、長いパッチはスクリプトファイルに書いてから実行している。

## 6. 2026-09-30 ロボットの主板・底板を 1 枚板にする

依頼: 「主板・底板をそれぞれ 1 枚の MDF でやりたい。小さくなってもいいから、どっちのバージョンも作って」

- **元データ**: `auto-trash-navigator/ATN_print/_individual_parts` の STL(3D プリント用に 4 分割)。読むだけで、そのプロジェクトは変更していない。
- **主板**: 400×400mm、角 R15、車輪用の切り欠き 4 か所。上の平らな部分(厚さ 5mm)の下に柱が 8 本(Ø14、高さ 43mm)。
  穴 75 個のうち 24 個は継ぎ板用。
- **底板**: 400×400×3mm、車輪用の切り欠き付き。穴 40 個のうち 32 個は継ぎ板用、8 個(Ø6.5)は柱のネジ穴。

作ったもの:

- **`slice` コマンド**(`src/stl_slice.py`): STL を水平に輪切りにし、複数の STL を偶奇規則で 1 つの形に合体、
  継ぎ板の下の穴を取り除き、円い穴は直径を復元して CIRCLE で書き出す。
- **`jobs/atn_half_scale/make.py`**: 両方の板を **1/2 スケール(200×200mm)** で生成。
  - 継ぎ板用の穴を取り除く(主板 24 個、底板 32 個)
  - 主板に、柱の位置の穴を 8 個追加(板 1 枚では柱を作れないので、スペーサーとネジでつなぐ。1/2 で Ø3.25 = M3 が通る。柱の高さは 1/2 で約 21.5mm → 市販の M3 20mm スペーサー)
  - 板 2 種 × 板厚 2 種 × (レーザー切断用・手切り用)= 8 通りの G-code

途中で、Ø1.7 の穴 1 個が「円」と判定されないバグが見つかった(→ 10 章)。

**未確認**: 板の実寸(200mm 角 + 余白が入るか)。取り付け穴 Ø1.7 は元の M3 用の穴を半分にしたもので、M3 は通らない。

### 6 周でも貫通せず。「ソフトが悪いのでは」を確かめる試験を作った(同日、さらに後半)

- **ユーザー報告(事実)**: `out/mdf_2_5mm/check6.gcode`(20mm 角 2 つ、100% で 400mm/min × 6 周 と 500mm/min × 6 周)でも
  **貫通しなかった**。問い: 「ソフトが悪いんじゃない?」
- **矛盾(事実から)**: 6mm 板は 600mm/min・1 周で約 1mm 入った(手触り)。同じ比率なら 2.5mm は 600mm/min で 3 周前後で抜けるはず。
  400mm/min × 6 周で抜けないのは、材料の違いだけでは説明しにくい → **何かが大きくずれている**
- **ソフト側で残っていた唯一の疑い(推測)**: M4(速度に合わせて出力を変える)が、この機械(Falcon2 のファーム)で想定より弱く効いている。
  G-code の構造そのものは 09-30 に解析済みで不備なし
- **作ったもの**: `out/checks/m3_m4.gcode`(+ 枠確認 `m3_m4_frame.gcode`、生成スクリプト `jobs/diagnostics/make_m3m4.py`)。
  30mm の線 4 本を 1 周ずつ: Y80 = M4・400 / Y88 = **M3**・400 / Y96 = M4・200 / Y104 = **M3**・200(すべて S1000)。
  通常のツールは M3 を禁止しているので手で組み立て、M3 を M4 に置き換えたものを通常の安全検証に通し、
  M3 の直後が G1 1 行・その次が M5 であることを個別に検査した
- **判定のしかた**: M3 の線が M4 よりはっきり深い → M4 が弱く効いている(ソフト側で M3 に切り替えて解決できる)。
  同じくらい → ソフトではなく、焦点・レンズ・材料(下記)の問題
- **ほかの有力な候補(推測)**: (1) 2.5mm の板が MDF(中質繊維板)ではなく **ハードボード(硬質繊維板)** かもしれない(薄い板に多く、
  密度が高くて切りにくい。表示の確認が必要)、(2) 焦点の段、(3) レンズ・保護ガラスの汚れ(MDF の煙ですぐ曇る)

### M3/M4 比較の 1 本目で火焔検知。速い比較と、紙での出力確認を用意(同日、さらに後半)

- **事実(LaserGRBL のログ)**: `m3_m4.gcode` の **1 本目(M4・S1000・400mm/min、30mm)を焼いた直後に FIRE**(火焔検知)で停止。
  直後の `M5` が `error:09`(アラーム中の命令拒否)。M3 の線までは進まず、**比較はできなかった**
- **調べたこと**(出典は下):
  - LightBurn フォーラム「Falcon2 S value/variable power issue」: 出力が極端に弱かった原因は **S 値の最大と `$30` の不一致**。
    この機械は `$30=1000`・このツールも S1000 = 100% で一致しているので **当てはまらない**(事実)
  - Creality フォーラム「Falcon2 22W lost more than half of its power」: 以前 400mm/min・100% で切れたものが 100〜200 でないと
    切れなくなった。レンズ・焦点・エアアシスト・`$30` を確認しても直らず、**4 つのレーザーダイオードの一部劣化** が疑われた(未解決)
  - Creality フォーラム「Cut bricht ab wegen Feuer Meldung」: Falcon2 22W で **遅い速度・80〜100% だと火災メッセージで中断** する。
    回避策として「速くして周回を増やす」が挙がっている
  - Falcon2 独自の `$152`・`$156`〜`$161` の意味(火焔センサーの感度か)は、資料が見つからず **不明**。触らない
- **判断**: 「遅い速度・100%」は、この機械では火焔検知に当たりやすい領域(公式フォーラムにも同じ報告)。
  ソフトの不備ではなく機械側の振る舞い。ただし、出力そのものが落ちている可能性(ダイオード劣化・レンズ)は残る
- **作ったもの**(`jobs/diagnostics/make_checks2.py`、どちらも安全検証済み):
  - `out/checks/m3_m4_fast.gcode`: 炎が出にくい速さでやり直す M3/M4 比較(100%・1 周、Y112 = M4 1200 / Y120 = M3 1200 /
    Y128 = M4 800 / Y136 = M3 800、線の間 5 秒)
  - `out/checks/paper_test.gcode`: **クラフト紙 0.2mm をメーカー公式の条件(80%・4000mm/min・1 周)で切る** 30mm 角と、
    50% の 30mm 角。公式条件で紙が切れなければ、機械の出力が落ちている疑いが強い(速いので火焔検知にも当たりにくい)
